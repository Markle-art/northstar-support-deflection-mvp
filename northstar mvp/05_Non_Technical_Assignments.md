# Non-Technical Member Assignments

Each of these four roles can work independently and in parallel with the Technical Lead's build — their outputs feed directly into what gets built and tested.

---

## Product Lead — Mark Ochieng

**Tasks:** T3 (Problem Statement & User Stories), T4 (MVP Scope Definition)

**Expected output:**
- A short problem statement (3–5 sentences) describing the support ticket pain point
- 3–5 user stories in the format: "As a [customer], I want to [action], so that [benefit]"
- A scope doc listing what's in vs. out (can reuse the "Deliberately Out of Scope" list from the MVP Design doc as a starting point, then confirm with Technical Lead)

**What to put on the board:** T3 and T4, moved to "Done" the same day each doc is finalized and shared

**Evidence to produce:** The user stories doc and scope doc, each with an edit-history timestamp (Google Docs version history is enough)

**How it connects:** This is the foundation everyone else builds on — CX Lead maps the journey against these stories, Technical Lead builds only what's in scope, QA tests against the stories directly

## Customer Experience Lead — Grace Murigi

**Tasks:** T5 (Customer Journey Map), T6 (Widget Copy & Script)

**Expected output:**
- A journey map/flowchart showing every step a customer takes through both flows, including the not-found/fallback path (can be built in any diagramming tool, or even a clearly labeled flow in a doc)
- A full copy doc with the exact wording for: greeting message, category button labels, input prompts, success responses (order + stock), fallback/escalation message, "anything else?" prompt

**What to put on the board:** T5 and T6, moved to "Done" the same day each is finalized

**Evidence to produce:** Journey map file/screenshot; copy doc

**How it connects:** The Technical Lead implements the widget using this copy word-for-word (T10 depends directly on T6) — this is what makes the CX Lead's contribution genuinely visible in the final demo

## QA & Testing Lead — Loureen Shillah

**Tasks:** T11 (Write Test Scenarios), T12 (Execute Tests & Log Results)

**Expected output:**
- A test case document with at least 8 scenarios (see the QA Plan doc in this package for a ready starting set you can use or expand)
- Completed results: actual outcome + pass/fail for each case, with screenshots as evidence, and any bugs reported back to the Technical Lead

**What to put on the board:** T11 moved to "Done" once test cases are written (can happen before the build is finished); T12 moved to "Done" once all cases are executed and logged

**Evidence to produce:** Test case doc (before build) + completed results doc with screenshots (after build)

**How it connects:** QA tests directly against the user stories (Product Lead) and the built widget (Technical Lead) — this is the proof, in the pitch, that the MVP actually works as claimed
